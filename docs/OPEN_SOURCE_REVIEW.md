# 开源方案调研与选型

调研日期：2026-10-28

## 结论

没有找到一个能够原样满足“中文 TXT 智能拆章 + 指定章节范围 + 可编辑校对规则 + 自定义每批章节数 + 并发批处理 + FreeLLMAPI 启动器 + 进度可视化 + 完成后自动合并导出”的现成项目。

因此采用“参考成熟开源项目的工作流设计，自研轻量本地工作台”的方案，不直接复制 GPL/AGPL 项目代码，避免许可证传染与无关功能负担。

## 重点参考项目

### 1. 书童 Pagekin / AI-Novel-Writer

- 地址：<https://github.com/EthanYoQ/AI-Novel-Writer>
- 许可证：GPL-3.0
- 可借鉴：TXT/MD/EPUB 按章导入、本地优先、OpenAI 兼容模型配置、任务侧栏、取消/暂停、TXT 导出。
- 取舍：功能很完整，但重点是小说创作和人工逐章审稿，许可证为 GPL-3.0，直接改造成本和合规成本都偏高。本项目只参考交互与任务管理思路，不复制代码。

### 2. bilingual_book_maker

- 地址：<https://github.com/yihong0618/bilingual_book_maker>
- 许可证：MIT
- 可借鉴：长文本批处理、并发 worker、自定义 Base URL、断点续传、三阶段管线（提取 → 处理 → 导出）、配置指纹和源文件保护。
- 取舍：它的核心目标是翻译电子书，缺少小说校对规则面板和审校结果工作流。本项目借鉴其“可恢复管线 + 自动合并导出”结构。

### 3. snowflake-fiction

- 地址：<https://github.com/hestudy/snowflake-fiction>
- 许可证：MIT
- 可借鉴：章节范围审查、可配置检查规则、并发默认值 2、429 退避与重试。
- 取舍：它是 Claude Code 插件，没有 GUI，也不能直接使用 FreeLLMAPI。本项目采用其“并发默认 2、可降为串行”的经验。

### 4. StoryVoice

- 地址：<https://github.com/NickYCLin/story-voice>
- 许可证：MIT
- 可借鉴：EPUB/TXT 导入、持久任务、进度、取消、重试、候选版本完成后原子切换。
- 取舍：技术栈包含 .NET、PostgreSQL、Redis、Docker，适合服务化部署，但对于单机小说校对明显过重。本项目保留“任务可见、失败可重试、原稿不覆盖”的理念。

### 5. Novelix

- 地址：<https://github.com/zxerai/novelix>
- 许可证：AGPL-3.0
- 可借鉴：Web Studio、审计 → 修订管线、多模型路由、章节导入和 TXT/MD/EPUB 导出。
- 取舍：目标是自动写小说并维护复杂故事状态，且采用 AGPL-3.0；不适合作为本地轻量校对器直接改造。

## 最终架构

- 运行方式：本机 Node.js 22 + 浏览器工作台，不依赖数据库或外部 npm 包。
- 数据安全：源 TXT 只读导入；整理结果写入工作台 `exports` 目录，不覆盖原文件；模型密钥默认不落盘。
- 拆章策略：优先识别“第 N 章/回/节”，兼容中文数字、全角数字和阿拉伯数字；合并连续重复标题；识别倒序标题、跨书目录与异常跳号。
- 处理管线：规则清理 → 按范围选择 → 自适应分批 → 并发模型校对 → 结果校验 → 按章节号合并 → 自动导出 TXT 和 JSON 报告。
- 模型协议：默认 `http://127.0.0.1:3001/v1`、模型 `auto`，兼容 FreeLLMAPI；同时支持任意 OpenAI Chat Completions 兼容端点。
- FreeLLM 集成：工作台内提供“启动 FreeLLMAPI”按钮，调用用户给出的 VBS；项目内也保留该脚本副本。

## 默认批次建议

对《百世飞升》实测，单章平均约 4,357 字符。5 章合并会形成约 21,800 字符的输入，若模型需输出等长正文，完整上下文可能超过 40,000 字符，免费模型更容易超限或截断。

因此默认值设为：

- 每批 3 章；
- 并发 2 批；
- 同时在途约 6 章；
- 单批字符上限 18,000，超出时自动提前切批；
- 遇到 429/5xx/超时自动退避重试；
- 用户可把每批章节数和并发数调高，但界面会实时显示“预计同时在途章节数”。

这个默认值与现成开源小说工具常用的并发 2 一致，同时更适合 FreeLLMAPI 的免费模型池和当前小说的实际章节长度。
